# Go Service Structure Implementation Plan

**Goal:** 整理 Go 服务职责，统一响应、错误码、异常处理与可落盘的结构化日志。

**Architecture:** 保留 net/http、现有 Go 规则和 Redis 房间协议。入口放在 cmd/server；internal/app 负责装配和退出；httpapi 负责传输；service 负责账户业务；repository/mysql 负责持久化；room 按连接、协议、房间、对局和广播拆文件。公共错误定义在 apperr，日志在 platform/logging。

**Constraints:** 不改变棋局计分规则；前端同步适配 HTTP envelope；WS 事件保持兼容。日志不记录请求体、密码、令牌和连接串。工作目录没有 Git 仓库，不创建提交。

- [x] 1. 公共错误与日志：稳定数值码、公开消息与内部原因分离，slog JSON 控制台和 lumberjack 轮转文件；测试脱敏、级别、并发和异常恢复。
- [x] 2. HTTP 与业务拆分：响应固定 code/message/data/requestId，集中处理鉴权、严格 JSON、404/405、访问日志、panic；账户服务依赖可替换的数据接口。用 httptest 和伪仓储覆盖成功、参数错误、鉴权、数据库故障、panic 和升级连接。
- [x] 3. 房间模块拆分：连接生命周期与协议独立，错误码复用 apperr；日志覆盖连接、走子、匹配、广播、结算失败；读写、AI、订阅和后台检查均有恢复边界。验证并发关闭与消息发送无 panic。
- [x] 4. 启动和配置：cmd/server 精简入口、依赖超时、优雅关闭、配置校验、healthz/readyz。移除源码中的真实连接凭据，迁移到权限受限且忽略提交的本地配置。更新构建脚本、环境示例和开发文档。
- [x] 5. 全链路验证：go test -race ./...、go vet ./...、前端构建、HTTP/WS 冒烟与人机对局；确认日志文件、错误响应和退出行为，再更新本地预览。

每项先补关键回归测试再实现；仅对独立日志子任务并行实施，集成和验收统一完成。
